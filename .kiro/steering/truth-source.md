# 断言的真值必须可追溯

> 这条规范来自 2026-07-30 的一整天实测。当天大部分时间不是花在写功能上，
> 而是花在**发现自己的测量和假设是错的**。八次错误有同一个形状，
> 修复也有同一个形状 —— 值得固化成规范。

## 规则

**任何写进文档、断言、日志的数值或事实，必须能追溯到「正在运行的那个二进制」
或编译出它的那棵源码树。追溯不到就如实标注为估算，不要写成事实。**

推论四条：

1. **判据的真值优先从文件/运行时读，不写死。** 能 `grep` 出来的阈值就别写成常量。
2. **只按名字匹配不够，要确认对象真的活着。** ROS 话题、进程、设备节点同理。
3. **发命令之后必须验证结果，不能假设成功。** 尤其是会改变物理状态的命令。
4. **间接信号不能替代直接判据。** 日志里挨着出现的一行、"看起来接近 0" 的读数、
   工具的默认假设，都不是判据。

## 当天的八个实例

留着是因为抽象规则容易被读过就忘，具体形状才记得住。

| 错在哪 | 表面症状 | 真正的判据在哪 |
|---|---|---|
| 期望值抄自另一棵 PX4 源码树 | 「100 Hz 偏离期望 50」的假失败 | 运行时读被编译那棵树的 `dds_topics.yaml` |
| 串口带宽全靠估算 | 60,060 B/s / 占满 100.3% | 飞控自报 `Payload tx` + 订阅端实测，两源交叉验证 |
| 用 `ros2 topic hz` 量发布率 | 同一系统两轮读数 50.0 / 21.4 Hz | 消息内 `timestamp` 的间隔（对丢包免疫） |
| 话题名只按正则匹配 | 节点全程「与飞控无连接」 | 加 `count_publishers>0`，排掉别人留下的幽灵话题 |
| `pkill -f 'px4 '` | 孤儿进程静默破坏下一轮测试 | 覆盖真实命令行：`px4_sitl` / `bin/px4` / `gz_x500` |
| 以为 `--symlink-install` 是链接 | 改完源码跑的还是旧代码 | `python3 -c "import m; print(m.__file__)"` 再 grep 标记 |
| 用 `nav_state` 判降落阶段 | 高度从 8.4 m 掉到 -0.04 m 却一直报"返航" | 垂速与高度（PX4 的 RTL 全程都是 `AUTO_RTL`） |
| 看紧跟 `Failsafe activated` 的日志行判原因 | setpoint 断流被误判成电池告警 | `failsafe_flags` 的分原因标志位 |

另有两次是**假设而不验证**：脚本发了 `commander arm` 就当已在飞行，
于是把静止数据当飞行数据报了出来（两组数字几乎一样，本该立刻起疑）；
测试用固定 `sleep` 等节点就绪，睡太短就拿到「与飞控无连接」的假失败。

## 落到实践

- 数值型断言写成「上限从配置读 + 下限显式声明为我们的要求」，别写成单个魔数
- 时间性等待写成「等到某个可观测判据成立」，别写成 `sleep N`
- 需要状态变更的操作，验证后再往下走，失败要区分「被拒（带原因）」与「无响应」
- 拿不到直接判据时，在文档里写明「这是估算/推测，未坐实」，并留下坐实的方法
- 推翻旧结论时保留原文加删除线 + 撤回理由，不要直接删 —— 审计轨迹比整洁重要

## 反面提醒

这条规范的成本是真实的：当天为了坐实一个结论，做过受控 A/B（`UXRCE_DDS_SYNCT`
开关各 90 s）、两源交叉验证（订阅端 vs 飞控自报）、纯函数单测（合成数据喂估计量）。
但收益也是实的：同一套集成测试从「三次误报」变成 13/13，
而且撤回了一个已经写进论文素材的错误数字。

判断标准是**后果**：会流进论文、会决定硬件选型、会影响飞行安全的断言，
值得付这个成本；一次性的排查脚本不必。
